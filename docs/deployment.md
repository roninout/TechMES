# Развёртывание TechMES

Maintenance находится на Primary, 192.168.1.118. Secondary приложений — 192.168.1.132.
Компьютер 192.168.1.131 относится к PostgreSQL; этот сценарий не меняет БД или репликацию.

## Разработка: General → Deploy

1. В Settings → Server выбрать настоящий TechMES.sln и перезапустить Maintenance.
2. Запустить Maintenance от администратора. На машине сборки нужен .NET SDK 10.
3. Нажать Deploy all. Сначала проекты собираются в отдельную папку. При ошибке сборки службы продолжают работать.
4. После успешной сборки установщик проверяет пути и файлы, делает резервную копию, останавливает Web → Calc → Runtime, заменяет файлы и запускает Runtime → Calc → Web.
5. Ожидается `Deploy all finished successfully`. Существующие appsettings*.json сохраняются побайтно.

Deploy all не обновляет работающую Maintenance. На первой локальной установке её настроенные source-appsettings копируются только в ещё не установленную службу.

## Общий пакет для двух серверов

1. Рядом с Deploy all нажать «Создать архив». Выбрать локальную папку. Будет создан автономный ZIP win-x64 с Runtime, Calc, Web, Host и Maintenance. Службы при сборке архива не останавливаются.
2. Открыть отдельное меню Deployment. Выбрать ZIP.
3. Заполнить оба профиля: компьютер, фактическая папка установки, сетевая папка доставки, локальный URL проверки Runtime, компоненты.
4. Primary: компьютер 192.168.1.118, путь по текущей установке, обычно C:\TechMES. Secondary: 192.168.1.132, обычно D:\TechMES. Путь профиля должен совпадать с установленными службами.
5. Maintenance по умолчанию выбрана только для Primary. Для её обновления приложение на целевом сервере нужно закрыть.
6. Нажать «Подготовить комплект». В новой локальной папке появятся:
   - TechMES_Deployment.zip — один и тот же архив для обоих серверов;
   - Deploy-Primary.ps1;
   - Deploy-Secondary.ps1.
7. Обе копии скриптов также включены внутрь общего ZIP. После изменения параметров установки комплект нужно подготовить повторно.
8. Send около сетевого пути копирует общий ZIP и подходящий скрипт в новый подкаталог назначения. Используется текущий доступ Windows. Удалённого запуска, WinRM, смены учётной записи и задач SYSTEM нет.
9. При отказе Send открыть папку комплекта и скопировать ZIP со скриптом вручную. Ошибка доставки не удаляет локальный комплект.

## Запуск на Secondary

1. Скопировать TechMES_Deployment.zip и Deploy-Secondary.ps1 в одну папку на 192.168.1.132.
2. В PowerShell от администратора, открытом в этой папке, выполнить:
   `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Deploy-Secondary.ps1`
3. Скрипт проверит компьютер и версию пакета, распакует ZIP в отдельную рабочую папку, проверит SHA256, создаст резервную копию и обновит выбранные компоненты.
4. Ожидается `SUCCESS. Selected services are running. Existing appsettings files were preserved.` Runtime может быть Active либо Standby.
5. При сбое обновления установщик возвращает прежние файлы и исходные Running/Stopped состояния. Если откат не завершился, это явно отмечается `ROLLBACK INCOMPLETE`.

Для Primary без исходников выполнить аналогично Deploy-Primary.ps1. Скрипт также умеет запросить повышение прав при обычном запуске. Скрипты можно запускать из полностью распакованного ZIP; лежащий рядом общий ZIP вручную распаковывать не требуется.

## Настройки и журналы

- Профили Maintenance: %ProgramData%\TechMES\Maintenance\package-deployment.json.
- Журнал каждого запуска: %ProgramData%\TechMES\DeploymentRuns\<запуск>\deployment.log.
- Резервные копии: %ProgramData%\TechMES\Updates\<запуск>.
- Рабочие `appsettings*.json`, локальные данные и закрытые сертификаты сохраняются. Архив содержит отдельные стартовые настройки для Runtime, Calc, Web и Host. Установщик проверяет их контрольную сумму и добавляет `appsettings.json` только там, где его ещё нет. Старый архив можно использовать для обновления установок с готовыми настройками. Для чистой установки через Deployment заново создайте архив и подготовьте комплект.
- С новыми настройками Runtime запускается в Standby до настройки PostgreSQL и CtApi. При начальной настройке обоих узлов задайте их роли и политику Runtime после подключения БД. Calc и Web используют локальный Runtime на порту `5101`, Web начинает с HTTP на порту `5163`, Host работает в режиме наблюдения. Проверка Deployment подтверждает запуск служб, а готовность к рабочим операциям проверяется после настройки зависимостей.
- Если служба ещё не зарегистрирована, скрипт создаст её после проверки конфигурации. Существующие учётные записи служб не меняются.
- Неизвестные пользовательские файлы не удаляются. При обновлении Maintenance удаляются устаревшие Tools/Deploy-TechMESSecondary.ps1 и Tools/Run-TechMESUpdate.ps1.
- PostgreSQL и его службы этим установщиком не управляются.

## Мастер PostgreSQL HA

В Maintenance откройте **Services → PostgreSQL → Мастер HA**. Для каждого компьютера используйте существующий профиль PostgreSQL. Если на компьютере БД установлен TechMES Runtime, выберите в профиле `Runtime` или `Auto`. Для сервера БД с отдельным Agent выберите `Standalone`.

### Создание первого Standby

В блоке **Создать первый Standby** используйте вкладку **Primary** на источнике и вкладку **Secondary** на компьютере назначения. Проверьте адреса и пути обоих профилей. Укажите администратора PostgreSQL и вводите пароли в полях мастера.

1. На Primary нажмите **Проверить Primary**. Maintenance покажет роль, версию, идентификатор кластера, базы и свободные ресурсы WAL. Нажмите **Создать techmes_repl**, если роли ещё нет. Сохраните сгенерированный пароль в защищённом месте. Существующая роль сохраняет свои атрибуты и пароль. Кнопка **Разрешить репликацию с Secondary** добавляет правило SCRAM для одного IPv4 и сохраняет копию `pg_hba.conf`. Приоритет более ранних правил сохраняется.
2. На Secondary нажмите **Проверить Secondary и доступ к Primary**. Maintenance покажет локальные базы и проверит вход администратора в `postgres` на Primary и физический вход `techmes_repl`. Для штатного комплекта администратор должен работать на обоих узлах. Для Primary требуется обычный SQL-вход с Secondary, а для локальной проверки на Secondary — вход через `127.0.0.1`.
3. Когда локальную БД можно остановить, нажмите **Подготовить Secondary и запустить Check** и подтвердите остановку. PowerShell запросит учётные данные локально. При успешной проверке служба назначения остаётся остановленной и отключённой до Apply. Если Check завершится ошибкой после остановки, скрипт попытается восстановить её исходный тип запуска и запустить. Уже остановленный и отключённый узел можно повторно проверить той же кнопкой.
4. Сверьте идентификаторы. После проверки данных прежнего кластера нажмите **Создать Standby (Apply)**. Штатный скрипт сохранит прежний каталог, установит копию кластера Primary и проверит применение WAL. Успешный результат в Maintenance показывает `streaming`, источник и слот.

#### Запуск экспортированного комплекта

Если Maintenance установлена только на Primary, экспортируйте комплект на вкладке **Secondary**. Запускайте его по инструкции ниже.

Откройте **Создать первый Standby** для новой установки. Источник берётся из профиля **Primary DB**, назначение — из **Secondary DB**. PostgreSQL 18 должен быть установлен на обоих компьютерах с одинаковым портом. На новом сервере нужен собственный инициализированный каталог данных и зарегистрированная служба PostgreSQL. Для работающей пары переходите сразу к **Проверке контроллеров**.

1. На Primary получите идентификатор командой `SELECT system_identifier::text FROM pg_control_system();`. Для первичной копии нужны доступ с нового сервера к порту PostgreSQL источника, вход администратора PostgreSQL в БД `postgres` и вход пользователя с правом `REPLICATION`. Для входа репликации в `pg_hba.conf` источника разрешите только IPv4 нового сервера, например `host replication techmes_repl 192.0.2.11/32 scram-sha-256` при использовании SCRAM. Проверьте, что Primary слушает свой сетевой адрес, `wal_level` установлен в `replica` или `logical`, доступны два процесса WAL sender и физический слот. На новом сервере разрешите вход администратора в `postgres` через `127.0.0.1`, чтобы скрипт мог проверить реплику после её запуска.
2. Введите адреса и идентификатор в мастере. Экспортируйте комплект и перенесите всю папку на новый Standby. **На новом сервере** остановите службу PostgreSQL и установите тип запуска **Отключена**. Откройте Windows PowerShell от администратора, перейдите в папку комплекта и выполните:

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Setup-Standby.ps1 -Mode Check
   ```

3. Введите учётные данные администратора и пользователя репликации в запросах PowerShell. Проверка показывает состояние `Ready`, адреса, исходный идентификатор нового сервера, слот и приблизительный размер копии. Она проверяет доступ к Primary и свободное место перед изменениями.
4. Выполните на новом сервере точную команду `Apply`, выведенную проверкой. Скрипт повторно сверит оба идентификатора, скопирует весь кластер через `pg_basebackup`, проверит копию через `pg_verifybackup` и сохранит прежний каталог назначения с суффиксом `.techmes-before-…`. Затем запустит службу PostgreSQL в автоматическом режиме и проверит устойчивый `streaming` и применение WAL до контрольной позиции. В папке комплекта появится отчёт `result-Apply-….json` со статусом `Initialized`, путём к старому каталогу и данными приёмника. После успешного создания переходите к проверке контроллеров.

Сценарий использует действующие настройки Primary и локальную конфигурацию нового сервера. В качестве назначения принимается остановленный экземпляр другого кластера. Установка с табличными пространствами на источнике или внешними и подключаемыми файлами конфигурации на назначении требует отдельной подготовки. При ошибке сохраните каталоги и отчёт. Если ошибка произошла после создания слота, проверьте его состояние и объём удерживаемого WAL на Primary перед повторным запуском.

### Проверка и настройка пары

1. Выберите узел в верхних карточках. Выполните проверку контроллера. Для удалённого компьютера запустите подготовленный комплект на целевом сервере и загрузите его `result.json`. Если контроллер требует подготовки, откройте соответствующую вкладку из мастера. Для новой пары после проверки обоих контроллеров разверните **Сетевая связь и сертификаты**.
2. Укажите базовый URL Runtime, который проверяет эту пару PostgreSQL. Если Runtime работает на компьютере с Maintenance, используйте его локальный URL, например `http://127.0.0.1:5101`. Нажмите **Проверить пару**. Мастер сверяет свежие ответы контроллеров и Runtime, показывает фактические роли, поток WAL, слот, отставание применения и результат проверки Main DB.
3. Перед плановым переключением нажмите **Проверить готовность**. Мастер опрашивает оба контроллера по mTLS. Они используют свои сохранённые учётные данные и проверяют одинаковую версию PostgreSQL, условия `pg_rewind`, место для копии PGDATA и реальный вход по протоколу репликации с каждого сервера на соседний. Результат отображается по каждому IP. После статуса **Готов** на обоих узлах можно открыть вкладку **Switching**. Эта проверка выполняется без остановки службы и запуска переключения.

   При первой настройке разверните **Правила pg_hba.conf для репликации в обе стороны** в пункте 3. На каждом узле проверьте действующий файл (`SHOW hba_file;`) и при необходимости добавьте показанное правило `host replication techmes_repl <IPv4 соседа>/32 scram-sha-256`. Для возврата прежнего Primary в качестве реплики доступ должен быть разрешён и на текущем Standby. На Windows сохранённые изменения применяются к новым подключениям без перезапуска PostgreSQL.

4. **Аварийное автопереключение PostgreSQL.** После проверки пары выберите узел в верхних карточках, установите нужное состояние флажка и примените настройку. Для перехода с Primary `.11` на Standby `.12` включите её на `.12`. Для обоих направлений настройте каждый узел отдельно и повторите проверку пары между настройками. На удалённом узле запустите команду с `-Mode Failover` из выданного комплекта и загрузите `result.json`. При изменении настройки перезапускается контроллер выбранного узла. Во время тестовой остановки PostgreSQL оставьте оба контроллера доступными по mTLS.
5. Выполняйте этот пункт, когда нужно изменить политику автовозврата. Выберите предпочтительный Primary в списке и в верхних карточках. Оставьте флажок **Включить автовозврат** снятым и нажмите **Настроить автовозврат**. Если этот узел удалённый, выполните указанный мастером скрипт и загрузите отчёт. Затем снова проверьте пару, выберите второй узел в верхних карточках и установите флажок. Примените настройку на втором узле или подготовьте для него комплект. Если политика изменилась, скрипт перезапускает службу контроллера. Когда фактический Primary находится на втором узле, включение автовозврата может инициировать переключение после проверок готовности.

### Первая настройка сетевой связи и сертификатов

В мастере укажите IPv4 обоих компьютеров БД, IPv4 компьютера с Maintenance, общий идентификатор кластера PostgreSQL и порт mTLS. Мастер подставляет идентификатор, если он совпал в двух загруженных отчётах контроллеров. По умолчанию порт mTLS — `5115`. Для каждого экспорта выберите папку на компьютере Maintenance. Мастер создаст отдельную папку комплекта с подпапками по IP серверов.

Скопируйте на каждый сервер всю его подпапку. На этом сервере откройте Windows PowerShell от администратора, перейдите в скопированную папку командой `Set-Location -LiteralPath 'C:\путь\к\папке'` и запустите:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Setup-Network.ps1
```

- **A. Подготовка узлов.** Запустите комплекты на обоих серверах. Если учётные данные для команд PostgreSQL ещё отсутствуют, PowerShell запросит их на каждом сервере. Перенесите в Maintenance оба файла `public.cer` в разных папках. Отдельно выпишите `CertificateSha256` с каждого сервера и введите его в соответствующее поле мастера.
- **B. Подключение узлов.** Выберите оба сертификата, укажите выписанные отпечатки и экспортируйте новые комплекты. Запустите их на серверах по очереди. Каждый комплект включает mTLS и перезапускает свой Runtime или Agent.
- **C. Сертификат Maintenance.** Нажмите кнопку подготовки в мастере на компьютере Maintenance. Подтвердите запуск PowerShell от администратора. После выполнения мастер подставит файл сертификата и его отпечаток.
- **D. Доверие к Maintenance.** Экспортируйте последние два комплекта и запустите их на соответствующих серверах по очереди. Каждый добавит доверие к сертификату Maintenance, правило брандмауэра для его IPv4 и перезапустит свой контроллер. Правила PostgreSQL для репликации в обе стороны указаны в пункте 3 мастера.

Успешный запуск создаёт в папке комплекта `result.json`. При ошибке в этой папке появляется `error.txt`. Закрытые ключи хранятся в системном хранилище сертификатов на компьютерах, где их выпустили. Затем выполните **Проверить пару**. Если есть активное переключение, мастер покажет идентификатор и направление плана и даст открыть вкладку **Switching**.
