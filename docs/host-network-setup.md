# TechMes Host: подготовка сети пары

Этап пункта 20: локальные проверки и взаимная диагностика по mTLS.
Общий IP ещё не назначается; Host работает в Observer. Runtime Active/Standby не определяет владельца будущего общего IP.

## Порядок подготовки

1. Обновить Host и Maintenance на обоих компьютерах. Открыть Maintenance от администратора; в Services указать действительный корень установленного TechMES.
2. Services → Host → Загрузить. Выбрать интерфейс, собственный IPv4, IPv4 второго компьютера, выделенный общий IPv4 и фактический префикс подсети. На втором ПК адреса узлов меняются местами; GUID интерфейса выбирается локально.
3. Проверить сеть на обоих узлах. Нужны статическая адресация, поднятый адаптер, собственный адрес Preferred с указанным префиксом; три разных адреса в одной подсети. Host не изменяет DHCP. Если DHCP включён, подготовить статическую адресацию отдельно с сохранением доступа к ПК.
4. Создать сертификат узла на каждом ПК. Приватный ключ остаётся в LocalMachine/My, не экспортируется. Обменять только публичные SHA256: собственный SHA256 одного ПК становится SHA256 второго узла на другом.
5. Включить защищённый endpoint на обоих ПК. Порт одинаковый (по умолчанию TCP 5117), отдельный от локального API Host 5116. Сохранить и перезапустить Host на каждом. При неудаче запуска восстанавливается исходный appsettings и выполняется повторный запуск; путь резервной копии показывается в отчёте.
6. Открыть firewall Host на обоих ПК. Правило PersistentStore разрешает входящий TCP только на собственный IPv4/порт и только от двух заданных IP. Используется сохранённый профиль, а не несохранённые поля.
7. Проверить второй Host с каждого ПК. Профили должны иметь обратные адреса узлов и одинаковые общий IPv4/префикс. В обоих отчётах ожидается localChecksPassed=true и пустой errors.

## Границы проверки

localChecksPassed подтверждает только локальные проверки. Это не сканирование адресного пространства и не доказательство свободы IP: общий адрес должен быть выделен администратором и исключён из DHCP.

Защищённые диагностические маршруты требуют клиентский сертификат с точным SHA256 своего или второго узла. Клиент проверяет SHA256 второго Host, срок, EKU и IP в SAN; произвольный сертификат и несовпадение имени отклоняются. Самоподписанная цепочка принимается только при совпадении pin. Рабочая служба должна иметь доступ к приватному ключу; стандартная установка использует LocalSystem.

Новые GET /api/host/network, POST /api/host/network/check и GET /api/host/shared-address/status не меняют сеть. Автоматический захват IP при потере связи здесь не реализован. Следующий этап — согласованная передача общего адреса с устойчивым состоянием и проверками перед назначением.

Проверка Windows cmdlets, реального сертификата LocalMachine, SCM, WPF и связи между двумя ПК выполняется на Windows. Кроссплатформенные тесты проверяют политику IPv4/DHCP, реальные TLS-соединения и отказ неизвестным сертификатам.
