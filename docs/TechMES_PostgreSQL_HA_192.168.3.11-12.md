# TechMES WEB — PostgreSQL HA на 192.168.3.11 и 192.168.3.12

Проверенный сценарий — 26 ноября 2026 года. База для переработки Maintenance — ветка `feature/Redundancy`, коммит [242f42a](https://github.com/roninout/TechMES/commit/242f42aa70caf1baaf1a1452fddc5005fc05efe7).

## Рабочая схема

- PostgreSQL 18 на Windows. Предпочтительный Primary — `192.168.3.11`. В штатном режиме `192.168.3.12` — Standby, физическая потоковая репликация идёт с .11 на .12. В исходной проверке использовался слот `techmes_primary`, отставание применения было 0 байт.
- Maintenance запускается на .11. На обоих серверах роль контроллера PostgreSQL выполняет `TechMES.Runtime.Service`. Служба PostgreSQL — `postgresql-x64-18`. Контроллеры управляют парой по mTLS. Для этой пары в History показан порт 5115.
- Аварийный failover выполняет текущий Standby. Для направления .11 → .12 настройка включается на .12. Для защиты в обоих направлениях включается на обоих узлах отдельно.
- Автовозврат настраивается на .12 с предпочтительным Primary .11. На .11 мастер требует отчёт о выключенном автовозврате. Когда .12 становится Primary и .11 восстановлен как Standby, .12 запускает отдельное плановое переключение после проверок стабильной репликации.

## Настройка пары в Maintenance

1. Открыть **PostgreSQL → Мастер HA**. Использовать профили двух серверов и режим контроллера Runtime или Auto. Проверить контроллеры в пункте 1.
2. Для новой пары пройти сетевую подготовку A–D **«Сетевая связь и сертификаты»**. A — подготовка узлов и получение их публичных сертификатов и отпечатков SHA-256. B — установка взаимного доверия узлов. C — подготовка сертификата Maintenance на .11. D — установка доверия к Maintenance на обоих узлах. Комплекты для целевого узла выполнять в Windows PowerShell от администратора.
3. В пункте 2 нажать **«Проверить пару»**. Для Maintenance на .11 используется локальный URL Runtime `http://127.0.0.1:5101`, если порт соответствует установке. Успешная проверка показывает фактические роли, поток WAL, отставание, доступную для записи Main DB и отсутствие активного плана.
4. В пункте 3 проверить готовность обоих узлов к плановому переключению и возврату через `pg_rewind`. Проверить действующий файл командой `SHOW hba_file;`. Для физической репликации роль `techmes_repl` должна проходить с соседнего узла в обе стороны. При необходимости добавить подходящее правило на каждом сервере.

```text
# На .11
host replication techmes_repl 192.168.3.12/32 scram-sha-256
# На .12
host replication techmes_repl 192.168.3.11/32 scram-sha-256
```

## Пункт 4 — аварийное автопереключение

1. После **«Проверить пару»** выбрать верхнюю карточку .12, включить флажок и нажать **«Экспорт настройки для выбранного узла…»**.
2. На .12 выполнить команду из экспортированного комплекта в Windows PowerShell от администратора. Передать режим явно. Обычный вызов скрипта без `-Mode` запускает проверку `Check` и не сохраняет политику.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Prepare-Controller.ps1 -Mode Failover -NoPause
```

3. Взять новый `result.json` по строке `Result:` и загрузить его в пункте 1 на .11 с выбранной карточкой .12. Признаки правильного результата — `Ready = true`, `PreparationCompleted = true`, `Failover.Enabled = true` и `FailoverEnabled = true`. В проверенном запуске на .12 скрипт вывел `Automatic PostgreSQL failover enabled: True on 192.168.3.12.`.
4. Для защиты в обратном направлении повторно проверить пару, выбрать карточку .11, включить тот же флажок и применить локально. При изменении настройки перезапускается Runtime выбранного узла. Вкладка Maintenance остаётся на .11.

## Пункт 5 — автовозврат на .11

1. Проверить пару. Выбрать .11 и в верхней карточке, и в списке **«Предпочтительный Primary»**. Снять флажок автовозврата и применить настройку локально. Этот шаг формирует отчёт об отключённой политике на .11.
2. Проверить пару повторно. Выбрать верхнюю карточку .12, оставить предпочтительным Primary .11, включить автовозврат и экспортировать новый комплект.
3. Выполнить на .12 из нового комплекта. Загрузить его `result.json` на .11 с выбранной карточкой .12. Успешный отчёт указывает включённый автовозврат и предпочтительный Primary `192.168.3.11`.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Prepare-Controller.ps1 -Mode Failback -NoPause
```

## Контрольный тест и наблюдения

- В тесте на .11 остановили только `postgresql-x64-18`. Контроллер Runtime на .11 и Runtime на .12 оставались доступны. Этот сценарий проверяет отказ службы базы. При потере контроллера .11 текущий алгоритм не сможет получить подтверждение Fence через mTLS.
- .12 автоматически выполнил `Fence → Promote`. До обновления восстановление было `Missing`, так как рабочий процесс завершался после Promote. Подтверждённый аварийный план оставался сохранённым на .12.
- После обновления Runtime автоматический обработчик продолжил сохранённый план. `Rejoin` вернул .11 в роли Standby, оба контроллера закрыли аварийный план. Запускать PostgreSQL на прежнем Primary вручную в промежутке не требуется. При `RebuildRequired` или `NeedsReview` план остаётся для разбора.
- Затем History показала отдельный завершённый переход .12 → .11. У обоих переходов `Fence`, `Promote` и восстановление — `Succeeded`. После проверки пары пользователь подтвердил итоговое штатное состояние .11 Primary, .12 Standby, WAL .11 → .12 в `streaming`, Main DB на .11 доступна для записи.
- History показывает timeline последней контрольной точки. При временном расхождении сразу после переключения смотреть свежую проверку пары и фактический приём WAL на Standby. Статус `streaming`, адрес отправителя и `pg_stat_wal_receiver.received_tli` показывают, откуда и по какой timeline поступает WAL.
- Тест доказывает восстановление ролей в этом сценарии. Для оценки потери подтверждённых транзакций при внезапном отказе нужно отдельно учитывать режим синхронизации и отставание WAL.

## Отдельные условия для Host и WEB VIP

- Координатор Host закреплён за узлом с меньшим IPv4. Для этой пары это .11. Он согласует передачу WEB VIP, когда оба Host отвечают и резервный WEB готов. Флажок автовыдачи VIP при отказе WEB достаточно включить на .11.
- .12 не избирается координатором при исчезновении .11. Если .11 — владелец и его Host штатно остановлен, служба снимает управляемый VIP с .11, а .12 его автоматически не получает. При аварийном завершении Host на работающей Windows VIP может остаться на старом интерфейсе.
- Если VIP уже у .12 и там остаются работоспособны интерфейс и WEB, потеря координатора сама по себе его не снимает. Новая передача или восстановление потерянного разрешения требует координатора.
- Возврат PostgreSQL на .11 и расположение WEB VIP — независимые операции. При восстановлении WEB прежнего владельца автоматического возврата VIP по предпочтению в текущем коде нет.

## Что важно показать при переработке интерфейса

Операция должна явно показывать целевой узел и его фактическую роль, предпочтительный Primary, сохранённую и подтверждённую отчётом настройку, стадию экспорта, выполнения и загрузки отчёта. После аварии нужны шаги `Fence → Promote → Rejoin` с текущей фазой и отдельным состоянием ожидания автовозврата. Настройки Host и PostgreSQL требуют отдельных подписей, поскольку срабатывают при разных отказах.

В первую очередь проверить и сделать понятным повторившийся случай — пользователь запустил `Prepare-Controller.ps1` без `-Mode`, получил успешный отчёт о проверке, но настройка осталась неподтверждённой.
