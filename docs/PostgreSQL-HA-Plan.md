## Первый блок кода

`MainDatabaseWriteGuard` получает готовые результаты существующего монитора, без новых SQL-запросов и таймеров. После обнаруженного конфликта он блокирует выдачу новых Main DB соединений и запрещает обход через другое подключение. Проверка повторяется перед передачей уже открытого соединения хранилищу.

Обнаруженный конфликт не снимается из-за Offline, старого снимка или отсутствия статистики. Для восстановления требуется последовательность свежих согласованных проверок Primary/Standby одного кластера со streaming replication. Используется существующий `Runtime:Redundancy:RecoveryThreshold`, по умолчанию 3.

Монитор состояния кластера устанавливает запрет до публикации нового снимка. Health worker отменяет текущую Runtime-сессию, не ожидая медленного локального SCM. Координатор Runtime прекращает работу при такой ошибке сразу, без ожидания обычного FailureThreshold. Диагностика остаётся доступной; рабочие HTTP-маршруты получают `database.write-blocked`.

Это реакция на обнаруженное противоречие в текущем процессе Runtime. Она не останавливает PostgreSQL, не закрывает прямые подключения других клиентов и не является физическим fencing. Недоступность компьютера сама по себе не доказывает остановку прежнего Primary и не разрешает повышение реплики. Состояние запрета пока хранится в памяти Runtime; подтверждение блокировки и журнал HA-операции должен хранить будущий локальный компонент управления.

База этого блока: `feature/Redundancy`, commit `769b9518b6bb0b4f6076da137c486cd64f0dd37a`. Изменения не требуют новых полей appsettings.
